# Git Templates And git-nest

Research notes on using git templates to seed git-nest's managed hooks
into fresh clones.

## What Git Templates Are

A git template is a directory whose contents are copied into every new
repository's `.git/` by `git init` AND `git clone`. Configured per-user
via `init.templateDir` or per-command via `--template=<dir>`. Common
contents: default hooks, `.git/info/exclude`, `config`, `description`.

Verified empirically (2026-08):

- `git clone --template=<dir>` copies template hooks + `info/exclude` into
  the clone (remote hooks are NOT cloned, so templates are the only way to
  seed hooks into a clone without post-clone steps).
- `git init --template=<dir>` does the same.

## Where Templates Could Help

### 1. Seeding The Managed Hooks Into Clones (biggest win)

git-nest's `hooks-install` currently must be run per checkout (or relies on
propagation to later-added subprojects). With a template:

- A user sets `git config --global init.templateDir <git-nest-template>`.
- Every future `git clone` (including `git-nest add`'s clones and
  `git-nest restore` re-clones) automatically gets git-nest's managed
  hooks in `.git/hooks/`, zero extra steps.

Caveats:

- The hook scripts git-nest writes are absolute-path wrappers
  (`"$write_hook_git_nest_path" __hook ...`). A template copy needs the
  git-nest install path baked in at template-creation time (fine if the
  template is generated by a `git-nest hooks-template <dir>` command from
  the resolved install path).
- Template-seeded hooks would be stale if git-nest is upgraded/moved.
  git-nest's `hooks-install` already rewrites managed hooks, so running it
  once after an upgrade refreshes them; a `git-nest doctor` check could
  warn when a hook's embedded path no longer exists.
- Hooks must tolerate running in a repo that is not (yet) a nest
  (git-nest's hooks already no-op gracefully -- they find the owning
  manifest or exit).

### 2. Seeding `.git/info/exclude` With Recovery-Backup Ignores

git-nest already maintains `.git/info/exclude` entries for
`.gitnest-recovery-*` on demand. A template could pre-seed them so an
interrupted conversion never shows stray files even before git-nest runs.
Minor: git-nest already self-heals this.

### 3. Default `config` For The Nest Root

A template can carry `[init] defaultBranch = main`-style defaults. git-nest
does not depend on this (tests set it explicitly); useful mainly for
consistency.

## Where Templates Do NOT Help

- `git-nest init` already creates the manifest + support files; the
  template would only add hooks/exclude, not replace init.
- The `[subproject]` manifest entries are workspace-specific and must stay
  user-managed; a template must NOT bake those in.
- Templates apply at repo creation time only; existing repos need
  `hooks-install` regardless.

## Recommendation

Worth doing as a small add-on, not a core feature:

1. Add `git-nest hooks-template <dir>` that writes the managed hooks +
   `info/exclude` into a template directory, resolving git-nest's own path
   at creation time.
2. Document:
   ```sh
   git config --global init.templateDir ~/.local/share/git-nest-template
   git-nest hooks-template ~/.local/share/git-nest-template
   ```
   Then every clone/init is git-nest-hooked automatically.
3. Optionally teach `doctor` to warn when a managed hook's embedded
   git-nest path is missing (stale template after upgrade).
4. Low priority: pre-seed `info/exclude` in the template.

Priority: low-medium. The main usability gap it closes is "hooks exist in
fresh clones without `hooks-install`"; `git-nest clone` already runs
`restore` and users can run `hooks-install` once, so this is convenience,
not necessity.
